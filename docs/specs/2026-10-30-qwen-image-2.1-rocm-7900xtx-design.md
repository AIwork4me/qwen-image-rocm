## 意图与动机（Why）

三个目标，逐层递进：

1. **性能目标**：在 Windows 原生 ROCm（gfx1100）上，把 ComfyUI + Qwen-Image-2.1 的出图速度推到这块 7900 XTX 的极限，同时画质不降或只略降。
2. **生态目标**：作者是 AMD 工程师。这个真实工作负载（diffusers + ComfyUI 两条栈、多种量化格式、多种注意力后端）就是 ROCm Windows 生态的压力测试。**任何 ROCm 相关问题 → 立即根因分析 → 最小复现 → 修复 → 向上游库提 PR**，以此持续完善 ROCm Windows 生态。
3. **开源目标**：全部过程公开——可复现的基准协议与脚本、原始数据、画质证据、问题 RCA 文档。公开证据既服务社区（其他 RDNA3 用户），也让 Phase 4 的上游 PR 更有说服力。

为什么先搭基线再优化：没有可信的基线数据，"极限优化"无从谈起。diffusers 直跑是显卡算力天花板参照；ComfyUI 与 diffusers 的差值 = 框架层损耗，是 Phase 3 判断优化空间的标尺。

### Phase 3 — 优化循环（核心）
每个实验 = **一个变量 + 速度测量 + 画质对比**，全部与 bf16 基线成对记录。候选手段（按预期收益排序，全部探索）：

1. **Turbo 8 步模型**（最大单点：40→8 步）；同时测量 Turbo 版画质落差。
2. **fp8 权重**（Comfy-Org fp8 checkpoint）。诚实预期：RDNA3 无原生 fp8 矩阵算力，收益主要来自显存占用减半 → 减少卸载/更大 batch，而非算力本身。
3. **GGUF Q4/Q5**（ComfyUI-GGUF 自定义节点）。预期难过画质关，仍实测。
4. **注意力后端**：ComfyUI 启动参数逐个对比（PyTorch SDPA 各后端、aotriton-flash 等），diffusers 侧用 SDPA backend 控制。
5. **torch.compile / Triton on Windows**：已知生态薄弱区，很可能是第一个上游 PR 机会。
6. **VAE tiling**：2048² 下 VAE 解码显存峰值优化。
7. **ComfyUI 显存模式**（`--highvram`/normal/lowvram 等）与缓存设置。
8. 过程中发现的其他手段，随时补入。

实验环境纪律：基线环境冻结；优化实验在副本/参数层做，保证任何基线数字可随时复现。

## 方案选型（已确认）

- **A. 双 venv 隔离（选定）**：Phase 1/2 各自独立环境，torch 均用指定命令。依赖栈完全隔离（ComfyUI 的 requirements 与 diffusers 新栈（transformers 5.x + 新 diffusers）有版本冲突风险），基线数据互不污染。代价：多 ~15GB 磁盘。
- B. 单 venv 共用：省磁盘，但装 ComfyUI 时可能破坏 Phase 1 已验证的依赖，基线可信度受损。否决——测数据是项目根基。
- C. WSL2：Linux ROCm 生态更成熟，但违背"Windows 原生完善生态"的使命。否决为主线，留作 kernel 缺失时的对照。

## 基准协议 v1

- **Prompt 集**：3 条固定（中文场景 / 英文场景 / 含长文字渲染的海报——Qwen 强项），文案在 Phase 1 实施时定稿，冻结于 `bench/prompts.json`，之后不得改动。
- **配置矩阵**：{1024×1024, 2048×2048} × 40 步（Turbo 对照实验用 8 步）× 固定 seed（3 个）。
- **测量**：每配置热身 1 次 + 正式 3 次；冷启动（首次加载权重）单独记录；报告热跑中位数，方差/极差同时入 JSON（见"开源质量承诺②"）。
- **公平对比规则**：跨框架（diffusers vs ComfyUI）与跨精度（bf16 vs fp8）对比，必须同调度器、同步数、同分辨率、同 seed 集；比较 Turbo（8 步）与完整版（40 步）时在结果中显式标注步数差异，不做跨步数的裸速度对比。
- **指标**：墙钟总时、文本编码耗时、去噪总耗时与 s/step、VAE 解码耗时、VRAM 峰值（`torch.cuda.max_memory_allocated` + 系统侧采样）。ComfyUI 侧另记节点级耗时。
- **输出**：`bench/results/<日期>/<实验名>.json` + 一页 Markdown 汇总（实验名规范：`p{phase}-{手段}-{分辨率}`）。

## 画质门槛协议

每个加速实验 vs `bf16-40步` 基线：同 prompt 同 seed，并排生成对比网格 PNG；LPIPS 数值作客观参考；结论三档（无感 / 略降 / 不可接受），**用户目检终审**。Turbo 的画质对照基线 = bf16 40 步（官方声明略降，以实测为准）。跨框架（diffusers vs ComfyUI）同 seed 图像不做逐像素一致要求（实现不同），只做质量级别对照。

## 作者代行的小决策（用户可推翻）

1. **ComfyUI 用 git clone + 自建 venv**，不用 portable 发行包（那是 CUDA 栈）。
2. **Python 版本**：优先 3.12，以 AMD 轮子实际支持为准。
3. **git 仓库**：本目录初始化 git 管文档/脚本/补丁。
4. **ComfyUI 基准执行方式**：走 API/workflow JSON 编程执行（可复现），不用手点 UI；UI 仅用于人眼验核。
5. **transformers/diffusers 版本**：以"能加载 QwenImage21Pipeline"为准 pin 并记录，不追新。
6. **ModelScope 规则的边界**：只约束模型权重，不覆盖 LPIPS 参考权重、自定义节点小资产等工具类下载。
7. **Phase 4 诊断用 torch**：RCA 需要非指定版本构建时，只进一次性诊断 venv，基线环境冻结不动。
8. **阻断性问题的最小绕过**：Phase 1–3 遇到完全阻断进度的问题，允许最小临时绕过以继续（绕过记为 issue），正式修复留给 Phase 4。
9. **开源仓库形态**：GitHub 公开仓库 `AIwork4me/qwen-image-rocm`，MIT License，README 含环境与复现说明。
10. **图像入库体积纪律**：单次推送图像 ≤100MB，只上对比网格 + 精选样张；原始大图本地留档不上传。
11. **语言策略**：上游工件全英文；README 英文为主 + 中文版（`README.zh-CN.md`）；仓库内工作记录可用中文。
12. **许可**：代码 MIT，基准数据/报告 CC-BY-4.0。
13. **CI 范围**：仅 lint/format + JSON schema 校验等 CPU 任务；不为跑通 CI 引入复杂度。
