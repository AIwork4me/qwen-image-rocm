Hit this from the ops side while downloading a ~60 GB model set
(Qwen-Image-2.1 split checkpoints) through an enforced-kill watchdog
(bandwidth scheduler). Quantified: across restarts, `hf download`'s
`{etag}.{uuid4}.incomplete` partials never resumed — each restart
re-fetched from byte 0, leaving **~38 GB of orphaned duplicate partials
for ~8 GB of actual progress** before we noticed the disk drain.

Since PR#4306 the temp name embeds a per-attempt uuid4, so a killed
process's partials are unreachable by the next run even though the
server supports ranged requests. We understand the real fix is xet-core
tracking (thanks for the pointer in-thread); for anyone stuck on
non-xet mirrors (our case: an hf-mirror with no xet) here is the
workaround we now run — parallel ranged `curl`-style chunks where **each
chunk file resumes byte-exact** (`curl -C -` semantics per range), so a
kill at any point wastes zero bytes:

[tools/download_parallel.py](
https://github.com/AIwork4me/qwen-image-rocm/blob/main/tools/download_parallel.py)
(stdlib + requests; safetensors header gate included).

Two things that might be cheap on the hub side, in case they help
prioritization:

1. `hf download` could at least **warn when it is about to orphan**
   existing `.incomplete` files above some size (or print their total),
   so the disk drain is visible instead of silent.
2. If resume-by-etag is on the table pre-xet, an explicit opt-in flag
   (`--resume-partials`) that reuses same-size partials would cover the
   mirror/enforced-restart niche without changing default behavior.

Data point for whoever picks this up: with 8 parallel chunk workers we
sustained ~40 MB/s against a mirror that throttles single connections to
~150 KB/s at peak hours, with zero duplicate bytes across restarts.
