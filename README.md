# qwen-image-rocm

Qwen-Image-2.1 image generation on **AMD Radeon RX 7900 XTX** under
**Windows-native ROCm** — reproducible baselines (diffusers + ComfyUI),
optimization experiments, and public evidence for the ROCm-on-Windows
ecosystem.

## Mission

1. Push image-generation throughput of ComfyUI + Qwen-Image-2.1 on the
   7900 XTX to its limit, with no or only slight quality loss.
2. Use this real workload to surface ROCm-on-Windows problems: every issue
   gets root-cause analysis, a minimal reproducer, a fix, and an upstream
   PR (see `docs/issues/`).

**Status: Phase 3 complete** (optimization loop: 5.2–5.5× at 1024², 2048²
unlocked; Phase 4 RCA next). See the
[design doc](docs/specs/2026-10-30-qwen-image-2.1-rocm-7900xtx-design.md) and
the [Phase 3 plan](docs/superpowers/plans/2026-10-31-phase3-optimization-loop.md).

## Setup

Prerequisites: Windows 11, AMD Radeon RX 7900 XTX (gfx1100), up-to-date
Adrenalin driver, [uv](https://docs.astral.sh/uv/), git.

The "stranger standard" one-command reproduction (30-minute bar):

```powershell
.\reproduce.ps1 -Quick    # one config: p2-en-scene, 1024², 40 steps, seed 42
.\reproduce.ps1 -Full     # the whole Phase 1 protocol (~1.5–3 h)
```

It creates an isolated `.venv-repro`, installs the pinned AMD ROCm stack,
smoke-tests HIP, downloads weights from ModelScope (~30 GB, once), and runs.

Manual equivalent (what `reproduce.ps1` automates):

1. `uv venv phase1-diffusers/.venv --python 3.12 --seed`
2. Install torch **only** with the mandated AMD wheel command (verbatim):
   ```
   python -m pip install --index-url https://repo.amd.com/rocm/whl-multi-arch/ "torch[device-gfx1100]==2.12.0+rocm7.14.1" "torchvision[device-gfx1100]==0.27.0+rocm7.14.1" "torchaudio==2.11.0+rocm7.14.1"
   ```
3. `python -m pip install -r phase1-diffusers/requirements.txt`, then assert
   `torch.__version__.endswith("rocm7.14.1")` (guards against a PyPI swap)
4. `modelscope download --model Qwen/Qwen-Image-2.1 --local_dir weights/diffusers-format`
5. `python -I phase1-diffusers/smoke_hip.py` (must report `gcn_arch=gfx1100`)
6. Set `QIR_SDP=math` (required on this stack — see finding 1 below) and
   generate: `python -I phase1-diffusers/generate.py --prompt-id p2-en-scene
   --width 1024 --height 1024 --steps 40 --seed 42 --out results/raw/repro`

Environment evidence for every result lives in `bench/results/env/`
(generated by `tools/snapshot_env.py`). The exact frozen dependency set is
`phase1-diffusers/requirements.lock.txt` (pip freeze; the ROCm stack is not
on PyPI, so the lock is AMD-wheel-index specific).

## Benchmark protocol

Frozen in [`bench/prompts.json`](bench/prompts.json): 3 prompts
(Chinese scene / English scene / text-rendering poster) × 40 steps ×
seeds `[42, 1337, 20261030]`. **Executed at 1024² only** — 2048² is
currently impossible on any working attention backend of the stock
Windows ROCm stack on a 24 GB RDNA3 card (see findings below). Results
are JSON (schema: `bench/schema/result.schema.json`) + Markdown reports
with medians, spread, and limitations.

## Phase 1 results (diffusers baseline, 1024², bf16, 40 steps)

Median of 3 measured runs per config; full reports:
[math](bench/results/2026-10-31-math-1024/report.md) ·
[flex](bench/results/2026-10-31-flex-1024/report.md)

| DiT attention | s/step (steady, median) | total s (median) | VRAM |
|---|---|---|---|
| math SDPA      | 3.60 – 3.70 | 239 – 254 | 18.8 GB |
| flex (no Triton) | 16.1 – 18.9 | 756 – 875 | 20.8 GB |

s/step = median of steps 2..40 (steady state); `step_times_s[0]` carries
text-encode + cpu-offload restore and is excluded (protocol v1.1 — see the
Limitations section in each report).

Environment evidence: `bench/results/env/snapshot-20261030-212234.json`.

## Phase 2 results (ComfyUI baseline, 1024², bf16, 40 steps)

ComfyUI 0.43.0 (pinned commit), own uv venv with the same mandated ROCm
stack, euler/simple/cfg-1 per the official Qwen-Image-2.1 template, API-
driven sequential queue, default attention (works out of the box — see
finding 5). Report:
[comfyui](bench/results/2026-10-31-comfyui-1024/report.md) ·
cross-framework grid:
[cross_framework.png](bench/results/2026-10-31-comfyui-1024/cross_framework.png)

| Framework (1024², warm) | median total (s) | s/step | VRAM |
|---|---|---|---|
| diffusers + cpu_offload (math) | 239 – 254 | 3.60 – 3.70 steady | 18.8 GB |
| **ComfyUI (default attn)** | **45 – 51** | ~1.1 (est. from exec time) | 16.6 GB |

ComfyUI is ~5× faster end-to-end warm at the same numerics: diffusers pays
~90 s/run of cpu_offload weight shuffling (31 GB over PCIe) plus a 3.66
s/step denoise loop, while ComfyUI keeps the DiT resident and swaps models
once per prompt (~350 s warmup per prompt switch, cached thereafter).
Framework-gap data is now the Phase 3 baseline. Note: per-step times are
not exposed by the ComfyUI API; totals are server execution times.

**Correction (Phase 3, 2026-11-01):** the 45–51 s steady-state excludes text
encode — measured runs differ from warmup only by seed, so ComfyUI's node
cache skips `CLIPTextEncode` (protocol v1.3 websocket timing made this
visible; real TE compute is 3–7 s bf16 / 1.1–2.6 s int8, see Phase 3).

## Phase 3 results (optimization loop, 2026-11-01, protocol v1.3)

Same session, same restart regime; every speedup is a paired ratio vs the
same-session bf16 shadow control (48.2 / 50.2 / 48.4 s per prompt).
Node-level timing (text-encode / denoise / VAE) and a true VRAM peak come
from the new websocket monitor. Full table:
[summary](bench/results/2026-11-01-phase3-summary/report.md) · per-experiment
`quality.md` + grids · [review pack](bench/results/REVIEW_PACK.md).

| Lever (1024², warm) | total (s) | speedup | quality (LPIPS vs bf16-40) |
|---|---|---|---|
| bf16 control (shadow) | 48.2–50.2 | 1.00× | — (noise floor 0.0000) |
| **Turbo 8-step + int8 DiT + ck-attention** | **9.1 uniform** | **5.2–5.5×** | distance 0.21–0.36 (user verdict) |
| Turbo 8-step + int8 DiT | 9.1–9.2 | 5.3× | distance 0.19–0.35 |
| Turbo 8-step (bf16) | 11.1–13.1 | 3.7–4.5× | distance 0.19–0.28 |
| ck attention alone (40-step bf16) | 35.2–37.5 | 1.30–1.37× | different numerics path (grid verdict) |
| int8 DiT and/or TE (40-step) | 44.5–50.5 | ~1.0× | fidelity 0.004–0.031 (near-lossless) |
| --disable-smart-memory | 42.4–46.4 | 1.06–1.14× | bit-identical |
| --highvram / --fast fp16_accumulation | p3 163 / 224 s | 0.22–0.30× (p3) | bit-identical (but slow) |
| torch.compile (diffusers side) | blocked | — | `TritonMissing` at inductor backend |

Highlights:

1. **2048² unlocked** (was "impossible on every backend", finding 2): native
   int8 checkpoints (DiT 7.26 GB + TE 9.35 GB) + sub-quadratic attention
   complete 2048×2048 — 328 s at 40 steps, **42.2 s with Turbo-int8**.
2. **Native int8 quantization is near-lossless and free**: plain
   `UNETLoader` auto-detects `.comfy_quant` checkpoints; speed parity at
   1024², half the weights. No fp8 exists for this model; w4a8 TE degrades
   conditioning (LPIPS up to 0.41) — int8 is the sweet spot.
3. **ck-attention (`--use-ck-attention`) is the only faster attention
   backend** on gfx1100 (1.30–1.37×); split is slightly slower, quad ==
   default, `--use-pytorch-cross-attention` is blocked by finding 1 even
   with a math-hard wrapper (the TE path re-arms broken kernels).
4. **Text-encode is cheap, model swaps are not**: fresh prompts pay 1.1–2.6 s
   TE compute (int8) but ~60–470 s of model swapping under RAM pressure —
   the real fresh-prompt cost on a 24 GB card with 31.8 GB of weights.
5. **Node cache is worth ~30%**: `--cache-none` runs at 0.68–0.71×.

## ROCm-on-Windows findings (Phases 1-4)

1. **flash & mem-efficient SDPA launch failures** —
   **upstream-root-caused** (TheRock#7315/#7992: AOTriton runtime/images
   mismatch in the torch 2.12.0+rocm7.14.1 Windows wheel),
   **verified locally** (weights-free 192-cell repro: fails from S=64;
   `2.12.0+rocm7.14.0` from the same index = zero launch failures),
   **remediation measured** (7.14.0 flash: 1.07 s/step @1024², 3.4x vs
   math, −1.9 GB VRAM) — [issue](docs/issues/2026-10-30-hiperrorinvalidvalue-qwen3vl-textencoder.md),
   [W2 evidence](docs/issues/evidence/phase4-w2-7140-verification.md)
2. **2048² (native resolution)**: attention no longer the blocker on the
   good 7.14.0 build (flash handles S≈16k), but bf16 VAE decode OOMs
   (20.25 GB conv alloc) on 24 GB — the measured 2048² route remains
   ComfyUI + native int8 (Phase 3: 328 s @40 steps / 42 s turbo).
3. **No Triton wheels for Windows ROCm** in AMD's wheel index (verified
   2026-11-01: TheRock PR#4006 merged but unpublished; nightly triton is
   Linux-only) → FlexAttention/torch.compile run slow fallbacks —
   [issue](docs/issues/2026-10-30-no-triton-windows-rocm.md)
4. **cpu_offload first-warmup pagefile thrash** (6× step time, recovers)
   on 32 GB RAM hosts; Phase 4 found the thrash cost is backend-dependent
   (flash immune, dense math allocations hit hardest) —
   [issue](docs/issues/2026-10-30-warmup-pagefile-thrash-cpu-offload.md)
5. **ComfyUI survives the SDPA backend bug via startup probe**: it hits
   the same flash-attention `invalid argument` failure, auto-disables it,
   and falls back to a sub-quadratic kernel — while diffusers/transformers
   fail the whole call. Same broken kernels, different consumer
   resilience; evidence (log line + both output SHA256s) in
   [issue 1](docs/issues/2026-10-30-hiperrorinvalidvalue-qwen3vl-textencoder.md).
   Phase 4 drafts propose porting that probe pattern upstream —
   [drafts](docs/upstream/INDEX.md) (all user-gated, unposted).
